# Roadmap interno — v0.11.0 Protocol additions

Design doc for the protocol-expansion sprint. Goal: ship five new transport options operators can flip on per-host (or per-fleet, post-v0.10), gated by per-protocol enable flags. ADRs travadas em sessões anteriores estão marcadas **[ADR]**; perguntas em aberto na seção [Open questions](#open-questions).

## Context

Reality + Hysteria2 cover ~95% of operator-reported network conditions in 2026. The other ~5% are:

1. **Hard-DPI national networks** (Iran, parts of CN, certain CGN-NAT broadband ISPs) where ALL probe-resistant transports get killed simultaneously. Operators need a WireGuard fallback because WG's anonymous-UDP shape is treated as "boring VPN" (rate-limited, not blocked).
2. **Cloudflare-fronted networks** where direct connections to non-CF IPs are throttled but CF-fronted HTTP/2/3 passes freely. Reality doesn't front; XHTTP and VMess+WS do.
3. **Legacy client compatibility** — some operator audiences (e.g. mainland China users running pinned forks of Hiddify v1.x) only support Trojan, not Reality or Hysteria2. Trojan-Go covers them without forcing a client upgrade.
4. **Cipher-family diversity** — a network operator who learns to fingerprint Xray's Reality TCP shape can't automatically extend that detection to Shadowsocks-2022's encrypted UDP shape. Different binary fingerprint = different fail mode under censor adaptation.

Five protocols is a lot. To keep the v0.11 release auditable, we phase by **shared infrastructure** (Block A: pure-Xray additions sharing one `xray.service`) → **separate daemons** (Block B: Trojan-Go + WireGuard) → **integration polish** (Block C: subscription, multi-node, docs). Operators flip each on independently of the others.

## Strategy at a glance

ADRs locked from prior sessions:

- **[ADR] Per-protocol enable flags, all off by default.** Adding a protocol is opt-in — operators don't get five new ports listening "by accident" after `s-vps update v0.11.0`. Matches v0.9's auto-update / backup / health-exporter precedent.
- **[ADR] Per-user credentials, server-generated by default.** Same pattern as Reality UUID + Hysteria2 password. Operators can override with explicit args (`s-vps user add bob --ss2022-psk ...`) for migration scenarios where the existing client already holds a known key.
- **[ADR] Schema bump v2 → v3, auto-migrated on load.** Each new protocol adds optional per-user fields (`ss2022_psk`, `wireguard_pubkey`, `trojan_password`, `vmess_uuid`). Auto-upgrade matches the v1→v2 migration in v0.9.

Consequences:

- **`users.index.json` schema v3.** v2 files auto-upgrade in memory on `state.load_users_index`, persist as v3 on next mutation. `fleet-receive` accepts both v2 and v3 payloads.
- **Multi-node aware from day one.** Every new protocol's URI builder takes a `FleetNode` so the subscription bundle on a control box gets N × P entries for the new protocols too. SS-2022 password is per-user (shared across nodes, like Hysteria2). WireGuard server private keys are per-node (like Reality keys).
- **`s-vps user add` gains new flags.** `--ss2022-psk`, `--wireguard-pubkey`, `--trojan-password`, `--vmess-uuid`. All optional; defaults to server-generated. Operators migrating from another setup pass the existing values.
- **Health exporter gauges add per-protocol.** `stealth_vps_unit_active{unit="trojan-go.service"}`, etc. The existing `stealth_vps_reality_port_listening` family extends to `stealth_vps_<proto>_port_listening`.

## Topology

Single-node v0.11.0 host with all five protocols enabled:

```text
┌─────────────────────────────────────────────────────────────────┐
│ stealth-vps host                                                │
│                                                                 │
│ /etc/stealth-vps/                                               │
│   users.index.json     (schema v3 — per-user fields per proto)  │
│   reality.state.yml                                             │
│   hysteria.state.yml                                            │
│   ss2022.state.yml      ← NEW (cipher + server PSK)             │
│   wireguard.state.yml   ← NEW (server priv key + listen port)   │
│   trojan_go.state.yml   ← NEW (server cert + listen port)       │
│   xhttp.state.yml       ← NEW (path + host header + listen port)│
│                                                                 │
│ Services:                                                       │
│   xray.service         — Reality + XHTTP + VMess+WS + SS-2022   │
│                          (one Xray, multiple inbounds)          │
│   hysteria-server.svc  — Hysteria2 (existing)                   │
│   trojan-go.service    — Trojan-Go (separate binary)            │
│   wg-quick@stealth.svc — WireGuard (kernel + wg-quick)          │
└─────────────────────────────────────────────────────────────────┘
```

Multi-node v0.11.0 host: the **control plane is unchanged** — it still only stores `users.index.json` + the fleet metadata. Data nodes each pick which protocols to terminate; per-node `*.state.yml` files capture the per-node parameters (e.g. WireGuard private key is per-node, ports are per-node).

```text
control ──SSH push─→ data-node-tokyo-1     (Reality + Hysteria2 + SS-2022)
                ──→ data-node-singapore-1  (Reality + Hysteria2 + WireGuard)
                ──→ data-node-paris-cdn-1  (XHTTP behind Cloudflare)
```

Subscription bundle for one user becomes N × P URIs where P varies per node. Hiddify Next handles heterogeneous bundles natively.

## Block A — Xray-side protocols (XHTTP + VMess+WS + SS-2022)

**Why grouped:** all three live inside the existing `xray.service` as additional inbounds in `/etc/xray/config.json`. No new systemd service, no new binary download, no new port range to firewall (operator picks ports from the existing Reality range). The role's `xray.yml` task gets three new optional inbound blocks; the headless reloader's render path handles them.

### Inbound: XHTTP

- **Use case:** Cloudflare-fronted traffic. The data node sits behind a CF Worker / Pages Function that proxies to `https://<vps>:443/<xhttp_path>`. Censors see encrypted CF traffic; the worker passes the payload to the VPS.
- **Listen:** `127.0.0.1:<random-port>`. Caddy (already on every control + most data nodes for the subscription endpoint) reverse-proxies the CF-fronted path to this loopback port. Operator-set `stealth_vps_xhttp_path` (e.g. `/.well-known/xhttp-stream`) gives clients a stable URL.
- **Per-user:** UUID (reuse `reality_uuid` from the index — same XTLS auth model). No per-user secret beyond what Reality already issues.
- **Per-node state:** `xhttp_path`, `xhttp_listen_port`, `xhttp_host_header`.
- **Open Question A1.** SHOULD XHTTP and Reality share the same UUID, or should `xhttp_uuid` be its own field? Default: share — one less field per user.

### Inbound: VMess+WebSocket+TLS

- **Use case:** legacy compat (older Hiddify, V2RayN, V2Box pre-2024). Worse fingerprint than Reality (TLS handshake is real, not stolen) — but most clients support it out of the box.
- **Listen:** `127.0.0.1:<random-port>`, fronted by Caddy on `443/ws-path`.
- **Per-user:** UUID. Per Open Question A1 default, reuse `reality_uuid`.
- **Per-node state:** `vmess_ws_path`, `vmess_ws_listen_port`.

### Inbound: Shadowsocks-2022

- **Use case:** different cipher family (AEAD with built-in obfs vs Reality's stolen-TLS shape). Useful when a network has learned to fingerprint Reality but hasn't trained against SIP022. Mature client support (sing-box, Shadowrocket, every modern Xray-based client).
- **Listen:** dedicated UDP+TCP port on `0.0.0.0:<random>`. Unlike XHTTP/VMess+WS, SS-2022 doesn't front through Caddy — it's a raw TCP/UDP endpoint.
- **Per-user:** **per-user PSK** in `users.index.json.users.<label>.ss2022_psk`. Server-generated default (base64-encoded 16/32 bytes depending on cipher). 
- **Per-node state:** `ss2022_method` (default `2022-blake3-aes-128-gcm`), `ss2022_server_psk` (a single PSK that's prepended to per-user PSKs per SIP022 multi-user model), `ss2022_listen_port`.
- **Open Question A2.** SS-2022 multi-user mode (SIP022) needs **both** the server PSK and the user PSK concatenated by the client. Operators have to handle this in the client config. Should the URI builder pre-concatenate (cleaner client UX but breaks if server PSK rotates), or emit them separately (cleaner rotation but more friction)? Default: pre-concatenate at render time; rotate-key on the server PSK regenerates all per-user URIs in one sweep.

### Implementation steps (Block A)

1. Extend `tasks/xray.yml` template to render XHTTP + VMess+WS + SS-2022 inbounds when the respective flags are true.
2. Add `tasks/ss2022_state.yml` (generates server PSK + records cipher choice + picks listen port). Same pattern as `reality_state.yml`.
3. Extend the headless reloader (`reloader.py`) to render the new inbounds from `users.index.json` + the new state files.
4. Add per-user fields to `users.index.json` schema v3: `ss2022_psk` (str, optional). XHTTP and VMess reuse `reality_uuid`.
5. Add URI builders to `urivider.py`:
   - `build_xhttp_uri(uuid, host, port, path, host_header, ...)` (vless://...?type=xhttp&...)
   - `build_vmess_ws_uri(uuid, host, port, ws_path, ...)` (vmess://base64({...}) form — vmess's URI is a base64-encoded JSON)
   - `build_ss2022_uri(server_psk, user_psk, host, port, method, ...)` (ss://base64(method:psk@host:port)#remark)
6. Extend `build_uris_for_user` to emit the new URIs per protocol enable flag. Extend `build_uris_for_user_multinode` to do the same per node.
7. Add `--xhttp-uuid`, `--vmess-uuid`, `--ss2022-psk` flags to `s-vps user add` (each defaulting to server-gen). Per Open Question A1 default, the XHTTP/VMess flags are aliases for `--reality-uuid`.
8. Tests: ~40 new pytest cases (URI builders, schema v3 migration, multi-node bundle includes new URIs).
9. Health exporter: add `stealth_vps_xhttp_port_listening`, `stealth_vps_vmess_ws_port_listening`, `stealth_vps_ss2022_port_listening` gauges.

**Estimate (Block A): ~4 dev-days.**

## Block B — Separate-daemon protocols (Trojan-Go + WireGuard)

These don't fit into the Xray inbound model. Each gets its own systemd service + state file + reloader hook.

### Trojan-Go

- **Use case:** legacy clients that only support Trojan. Niche but real.
- **Binary:** `p4gefau1t/trojan-go` upstream releases (Go binary). Pinned version via `stealth_vps_trojan_go_version`.
- **Listen:** `0.0.0.0:<random-port>` with TLS termination. Cert from acme.sh's existing `/etc/stealth-vps/tls/` symlink set (single-node) or per-node LE cert (multi-node).
- **Per-user:** `trojan_password` in users.index.json. Server-generated.
- **Service:** `trojan-go.service` (rendered template, hardened with `ProtectSystem=strict` + syscall filter — same pattern as Hysteria2 + bot).
- **Reload semantics:** like Hysteria2, Trojan-Go's SIGHUP routes into a graceful-shutdown path. Use `mode="restart"` in the Reloader (matches v0.7.3 fix for Hysteria).
- **Open Question B1.** Trojan-Go is in maintenance mode upstream (last release ~2023). Ship anyway with a "deprecated by 2027" note in the docs, or skip and recommend SS-2022 / XHTTP instead? Default: ship with the note. Operators with locked-in client populations need this.

### WireGuard

- **Use case:** ultimate fallback for hard-DPI networks. WG's UDP shape is well-known and most networks ALLOW it (treating it as "corporate VPN").
- **Binary:** `wireguard-tools` from Debian apt. No new download.
- **Listen:** `0.0.0.0:<random-UDP-port>`. Different port range from Hysteria2 (collision-avoidant defaults: 51000-52000).
- **Per-user:** **client public key** in `users.index.json.users.<label>.wireguard_pubkey`. The CLIENT generates the keypair (operator copies the pubkey into `s-vps user add bob --wireguard-pubkey ...`); the server only stores the pubkey + assigns an IP.
  - Server-generated default: server mints a keypair + stores the privkey under `/var/lib/stealth-vps/wireguard/<label>.privkey` for the operator to fetch via the bot/CLI on first add. Less "WG-native" UX but consistent with the rest of the project's UX.
- **Per-node state:** `wg_server_private_key`, `wg_listen_port`, `wg_subnet` (e.g. `10.99.0.0/24`).
- **Service:** `wg-quick@stealth.service`. Config rendered to `/etc/wireguard/stealth.conf` from the users.index.json template.
- **Reload semantics:** WG-quick supports `wg syncconf` for hot reload (no service restart). Use that.
- **Open Question B2.** Subnet conflict resolution: `10.99.0.0/24` is the default but might collide with operator's existing tooling (Docker, k8s overlay, etc). Should the role probe `ip route` to pick a non-conflicting subnet, or just let the operator override `stealth_vps_wg_subnet`? Default: let operator override. Document the default in the operator docs.
- **Open Question B3.** WG client gets a static IP (e.g. `10.99.0.5/32`). How is that allocated? Sequential? Hash of label? Random? Default: sequential (next-free in the /24), tracked in the index as `wireguard_client_ip`.

### Implementation steps (Block B)

1. **Trojan-Go:**
   - `tasks/trojan_go.yml` — download binary, drop systemd unit, render `/etc/trojan-go/config.json` from index.
   - `templates/trojan-go.service.j2`, `templates/trojan-go-config.json.j2`.
   - `tasks/trojan_go_state.yml` — picks listen port.
   - URI builder in `urivider.py`: `build_trojan_uri(password, host, port, sni, ...)`.
   - Per-user `trojan_password` field, server-gen default.
   - Reloader integration: when `trojan_go_enabled`, the reloader regenerates `config.json` + `systemctl restart trojan-go.service`.

2. **WireGuard:**
   - `tasks/wireguard.yml` — apt install wireguard-tools, generate server keypair, render `/etc/wireguard/stealth.conf` from index, enable wg-quick.
   - `templates/wg-stealth.conf.j2` — the WG-config template (server `[Interface]` + per-user `[Peer]` blocks).
   - `tasks/wireguard_state.yml` — generates server keypair + picks port + records subnet.
   - URI generation: WG doesn't have a standard URI. Render a `.conf` snippet per user that the user pastes into their WG client. The bot's `/sub` and the subscription file include the per-user conf inline (`[Interface]\nPrivateKey=...\nAddress=...\n[Peer]\n...`).
   - Reloader integration: `wg syncconf stealth /etc/wireguard/stealth.conf` (hot reload, no service restart).

3. **Tests (Block B):** ~30 new pytest cases (URI/conf builders, state file generation, schema v3 fields).

4. **Health exporter:** `stealth_vps_unit_active{unit="trojan-go.service"}` + `..."wg-quick@stealth.service"}`; `stealth_vps_trojan_port_listening`, `stealth_vps_wireguard_port_listening`.

**Estimate (Block B): ~5 dev-days.**

## Block C — Multi-node + sub bundle integration

Once Blocks A + B land, the existing v0.10 multi-node story extends:

1. **`s-vps fleet add` discovers ALL enabled protocols** on the data node. The `slurp_remote_yaml` step extends from `reality.state.yml + hysteria.state.yml` to also pull `ss2022.state.yml`, `trojan_go.state.yml`, `wireguard.state.yml`, `xhttp.state.yml` (whichever exist).
2. **`fleet/<id>.yml` schema adds per-node protocol blocks.** Each node records which protocols it terminates + the per-node parameters. Backwards-compatible: missing blocks mean "this node doesn't run this protocol."
3. **`build_uris_for_user_multinode` emits N × P × users.index protocols** — per-node URIs only for protocols the node actually terminates.
4. **Subscription bundle becomes heterogeneous.** A fleet with `tokyo-1` (Reality + Hysteria2 + SS-2022), `singapore-1` (Reality + WG), `cdn-1` (XHTTP) renders 4 URI types per user across 3 nodes. Hiddify Next handles this natively.

### Implementation steps (Block C)

1. Extend `stealth_vps.fleet.FleetNode` with per-protocol port/key blocks (`ss2022_port`, `wg_listen_port`, `xhttp_path`, etc) — all optional.
2. Extend `cli.cmd_fleet_add` slurp step to read the new state files.
3. Extend `bot_core.uri_config_from_node` to populate the new fields.
4. Extend `bot_core.build_uris_for_user_multinode` to emit per-protocol URIs per node.
5. Extend the molecule `multinode` scenario to enable one new protocol per data node + assert the subscription bundle has the expected per-protocol URIs.

**Estimate (Block C): ~3 dev-days.**

The full v0.11.0 cut covers Blocks A + B + C. ~12 dev-days estimated. Target cut date: 2026-06-30 if work starts immediately after this doc is approved.

If timeline slips: **Blocks A + C alone** ship as a "Xray protocol additions" interim release (v0.11.0-rc1 or directly v0.11.0); Trojan-Go + WireGuard slip to v0.11.1 / v0.11.2. The schema is forward-compatible (the WG/Trojan fields just stay null).

## Scope (out — explicitly deferred)

| Want | Why deferred |
|---|---|
| Reality fronting (Reality-as-XHTTP-server) | Reality already fronts via the `dest` masquerade. XHTTP is a DIFFERENT model (real TLS via CF). Two-layer Reality+XHTTP is not in Xray-core yet. |
| OpenVPN | Boring. Adds binary + cert mgmt + tons of attack surface. WireGuard covers the "boring VPN fallback" niche better. |
| WG over Tor | Niche. Tor-as-fallback is a separate v0.13+ design conversation. |
| TUIC | Hysteria2's predecessor; superseded. Hysteria2 is in the role already. |
| Per-protocol traffic accounting | Stats per-protocol per-user requires Xray's stats API or Hysteria's stats endpoint. Already shipped via `:9101` for Reality+Hy2. Adding for the new protocols is a v0.12+ observability story. |
| Per-user × per-protocol enable/disable matrix | A user is enabled or revoked across all protocols. Granular gating is interesting but adds schema complexity. v0.12+ if real demand. |
| Auto-pick a protocol based on client geolocation | Out of scope — clients handle that via Hiddify's latency probing across the multi-node bundle. |

## Schema v3

```json
{
  "version": 3,
  "users": {
    "alice": {
      "reality_uuid": "...",
      "hysteria_password": "...",
      "sub_token": "...",
      "created_at": "...",
      "enabled": true,
      "sub_expires_at": null,
      "ss2022_psk": "base64-16-or-32-bytes",
      "wireguard_pubkey": "base64-32-bytes",
      "wireguard_client_ip": "10.99.0.5",
      "trojan_password": "32-char-token"
    }
  }
}
```

Migration v2 → v3: on first `state.load_users_index` after upgrade, each user row gets the four new fields set to `null` (operator hasn't issued credentials for these protocols yet). The new URIs only render when both the protocol is enabled AND the user has a non-null value for the corresponding field. `s-vps user add bob` post-v0.11 generates values for whichever protocols are enabled.

`fleet-receive` accepts both v2 and v3 — data nodes running v0.10 won't crash when they receive a v3 payload (they ignore the unknown fields). Data nodes need v0.11+ to actually serve the new protocols.

## Decisions (locked 2026-05-20)

All 8 questions resolved with the operator. Defaults accepted; recorded here for the implementing dev.

| # | Decision |
|---|---|
| A1 | **XHTTP + VMess+WS reuse `reality_uuid`** — one fewer per-user field. |
| A2 | **SS-2022 URI pre-concatenates server+user PSK** at render time. Server PSK rotation re-renders all URIs. |
| B1 | **Ship Trojan-Go** with a deprecated-by-2027 note in `docs/operations.md`. |
| B2 | **WireGuard subnet:** `stealth_vps_wg_subnet` defaults to `10.99.0.0/24`; operator overrides if conflict. |
| B3 | **WG client IP:** sequential (next-free in the /24), persisted as `wireguard_client_ip` per user. |
| B4 | **WG keypair:** server-gen by default. Operator can pass `--wireguard-pubkey` to use a client-gen pubkey. |
| C1 | **Per-node protocol enable:** implicit — discovered from each data node's `*.state.yml` presence (matches v0.10's pattern). |
| C2 | **`fleet-receive` accepts schema v3 on v0.10 data nodes.** Unknown fields are silently dropped. Mixed v0.10/v0.11 fleet during rollout works without intervention. |

## What signals success

After v0.11.0 ships + a Tokyo+Amsterdam fleet smoke:

- **Single-node v0.10 → v0.11 is a no-op.** All new protocols default off; no listening port appears on a converged host that doesn't explicitly enable them.
- **`s-vps update v0.11.0`** migrates `users.index.json` v2 → v3 in memory + persists on next mutation. Operators don't see schema work in their flow.
- **Enabling SS-2022 on a single node:**
  ```bash
  STEALTH_SS2022_ENABLED=true s-vps update
  s-vps user add bob   # generates ss2022_psk + emits the URI
  ```
  The bot's `/sub bob` returns a subscription URL whose decoded body now includes an `ss://...` line alongside the vless:// + hysteria2:// entries.
- **WireGuard fallback:** `s-vps user add alice --wireguard-pubkey <pasted>` issues alice's WG config; she pastes it into her WG client; she connects. End-to-end < 60 seconds from operator's POV.
- **Multi-node + heterogeneous protocols:** a fleet where `tokyo-1` runs Reality+Hy2+SS2022 and `singapore-1` runs Reality+WG yields a 5-URI subscription bundle per user (Hiddify Next's auto-select picks the lowest-latency one that the client can actually negotiate).
- **532+ automated tests** (424 from v0.10 + ~70-110 new). No regressions in single-node or multi-node tests.
- **Two operator beta-testers** running a v0.11 fleet for 2 weeks before announcing.
